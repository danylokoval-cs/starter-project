## Власна реалізація і межі
 
DTO boundary: `RegistrationInput` → нормалізація (`Trim`) і перевірка довжин (userName/email ≤ 256, displayName ≤ 120, password ≤ 128) → `UserManager.CreateAsync` → `RegisterResponse(Id, UserName, DisplayName)`; `/api/me` повертає лише `CurrentUserResponse(UserId, UserName, Role)`; звідки `/api/me` та create беруть id: лише з claim `ClaimTypes.NameIdentifier` перевіреного principal (cookie Identity); заголовок `X-Demo-UserId` і поля тіла ігноруються, `CreateIncidentRequest` не має поля власника; cookie options і межа HTTP: HttpOnly, SameSite=Lax, Secure = SameAsRequest у Development / Always поза ним, редирект замінено на 401/403; фактичні flags: у браузері по http `path=/; samesite=lax; httponly`, Secure=false (Рис. 12, Рис. 13), тест через HTTPS перевіряє httponly, secure, samesite=lax, path=/; строк дії: не змінювався (cookie сесійна, `Expires: Session`; серверний квиток за типовими налаштуваннями Identity); однакові login-відмови: невідомий користувач і хибний пароль дають однаковий `401` без тіла й `Set-Cookie`, автотест A-07 порівнює статус, тіло без `traceId`, заголовки; обраний duplicate контракт: `409` з однаковим тілом для дубля імені й email (без назви поля, кодів Identity, значень), решта відмов — безпечний `400`, регресійний тест; rate partition/window/recovery і події: політика `login`, fixed window, ключ — IP (`RemoteIpAddress`, у тесті «unknown»), 10 запитів за 10 с, `QueueLimit = 0`, відповідь 429, відновлення перевіряє тест на свіжому host; події `EventType`/`Result`/`TraceId` (login success/failure, logout success, register); CSRF навчальний борг: POST із cookie без anti-forgery токена, частково знижено SameSite=Lax, повна модель — ЛР6; обрані поглиблення (відмінний): не входить до обраного рівня.
 
## Докази
 
Пояснення для всіх:
 
- **Маршрут довіри (CP-01):** JSON register → `RegistrationInput` (недовірені дані) → перевірка довжин → `UserManager.CreateAsync` (політика пароля, унікальність, хешування через `IPasswordHasher`) → Identity store `identity_users` → роль Reporter → безпечний `RegisterResponse`. Пароль не логується й не повертається.
- **Перевірка пароля:** `PasswordSignInAsync` знаходить користувача за нормалізованим іменем, порівнює пароль зі збереженим хешем через `IPasswordHasher` і лише за успіху видає cookie.
- **Cookie options і межа HTTP:** HttpOnly (недоступна скрипту: `document.cookie` порожній), SameSite=Lax, Secure залежить від середовища; по http у Development cookie без Secure — прийнятно лише локально.
- **Чому client UserId не доказ:** усе, що надіслав клієнт (поле форми, JSON, заголовок), може підробити відправник; особу доводить лише підписана сервером cookie, з якої middleware будує principal (A-03, A-05).
- **CSRF-борг:** див. вище; повний захист — ЛР6.
- **Канали перебору акаунтів:** `409` при реєстрації розкриває існування імені/email (тіло однакове, поле не названо); час відповіді входу може відрізнятися для існуючого й неіснуючого користувача, знижується rate limit; реєстрація без власного ліміту.

Компроміс: спільний NAT ділить квоту, за проксі потрібні forwarded headers. Події не містять пароля, cookie, хеша, токена, `Authorization`, тіла запиту й введеного імені при невдалому вході (туди часто помилково вводять пароль).
