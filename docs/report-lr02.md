## 2. Контракт і CP-01

Запит створення інциденту (`POST /api/incidents`) приймає окремий request DTO `CreateIncidentRequest` з чотирма nullable-полями: `title`, `description`, `severity`, `occurredAtUtc`. Відповідь — окремий `CreatedIncidentResponse` без ідентифікатора власника.

| Поле | Правило | Ключ у `errors` |
|---|---|---|
| title | обов’язкове; ≤ 160 символів (до Trim) | `title` |
| description | обов’язкове; ≤ 4000 символів (до Trim) | `description` |
| severity | `Enum.TryParse` (без урахування регістру) + `Enum.IsDefined`; «7» відхиляється | `severity` |
| occurredAtUtc | обов’язкове; не пізніше now + 5 хв; зберігається в UTC | `occurredAtUtc` |
| High/Critical | опис після Trim ≥ 40 символів (межа 39/40, T-09) | `description` |
| повторний title | активний (не Closed) інцидент з тим самим заголовком → 409 (T-03) | — |

Помилки валідації повертаються разом через `Results.ValidationProblem` (400, `application/problem+json`). Серверні поля (`Id`, власник, `Status = New`, часи) задає лише обробник; зайві поля JSON ігноруються (CP-01, рис. 26–27). Пробіли обрізаються один раз перед збереженням. Рішення вважати `title` і `description` обов’язковими прийнято в рамках цієї реалізації самостійно.

## 3. Security-сценарій і CP-02/CP-03

1. **Контекст і гіпотеза.** `GET /api/incidents/search` приймає `q` і `sortBy`; гіпотеза — обидва вставляються в текст SQL.
2. **Стан до.** Vulnerable commit `6ca837fa…`, п’ять навчальних записів (рис. 28, 30); звичайний пошук `q=USB` працює (рис. 31).
3. **Мінімальний сценарій (лише читання, локальний стенд).** Ввід S-01: `zz-no-match' OR TRUE -- `, порівняння зі звичайним запитом і запитом без збігів.
4. **Спостереження.**

| Вхід | `q` | Очікувано (ввід = дані) | Спостережено | Рис. |
|---|---|---|---|---|
| A | `USB` | 200, один запис | 200, один запис | 31 |
| B | `zz-no-match` | 200, `[]` | 200, `[]` | 32 |
| C | `zz-no-match' OR TRUE -- ` | 200, `[]` | 200, усі записи таблиці; `ORDER BY` і `LIMIT` відкинуті (порядок 0001, 0002, 0003…); `Parameters=[]` | 33, 37 |
| D | `O'Brien` | 200, один запис | 500 `problem+json`; в журналі синтаксична помилка біля «Brien» (SQLSTATE 42601) | 34, 38 |
| — | `комп'ютерного` | 200, один запис | 500 | 35 |

5. **Першопричина.** `src/SecureLab.Api/Scaffolding/Lab02Endpoints.cs` (vulnerable commit): рядок 16 — `sortBy` повертається як є; рядки 18–19 — `q` вставляється в текст запиту; рядок 20 — `FromSqlRaw` (рис. 39, 40). Фільтр апострофів чи `OR` не усуває механізму: дані й структура запиту змішані в одному рядку.
6. **Виправлення (CP-03).** Конкатенацію замінено LINQ з `EF.Functions.ILike(…, pattern, "\\")` та `EscapeLike` (спершу `\`, потім `%` і `_`); `sortBy` вибирається з allowlist `createdAtUtc | severity | status` (ранги Critical 0 … Low 3; New 0 … Closed 4; другий ключ `Id`), інше значення → 400 з ключем `sortBy`; `Take(50)`; response DTO `SearchIncidentResponse`. Diff: [evidence/cp03-diff.txt](evidence/cp03-diff.txt), рис. 63–64.
7. **Повторний і позитивний сценарії.** Той самий ввід S-01 → `[]` (S-02, рис. 44); у журналі значення — параметри `@pattern`, `@pattern0`, `@p` (рис. 51–52). Апостроф, `комп'ютерного`, буквальні `%`, `_`, `\`, `q=навчальн`, три варіанти сортування, `sortBy=price` → 400 (рис. 42–50, 53–56).
8. **Залишковий ризик.** Єдиний сирий SQL — статичний службовий `ExecuteSqlRawAsync` у `DatabaseBootstrap.cs:29` без вводу користувача. Захищено лише цей ендпойнт; нові місця доступу до БД потрібно переглядати окремо.

## 5. Обмеження і висновок

- Конфлікт T-03 перевіряється `AnyAsync` без унікального індексу: за двох одночасних створень обидва запити можуть пройти перевірку. Не відтворювалось.
- Гілку «повторний заголовок дозволений, якщо старий у статусі Closed» перевірено лише аналізом коду; порівняння заголовків чутливе до регістру.
- Синтаксично некоректний JSON і некоректний формат дати окремо не досліджувались.
- `Take(50)` на п’яти записах не спостерігається; екранування `%`, `_`, `\` перевірено на даних, що не містять цих символів (очікувано `[]`).
- Не виконувалися вимоги рівня «Відмінно»: автоматичний S-02 на множині результатів, T-10, A-02.

Висновок: контракт створення інциденту перевірено; SQL injection у пошуку відтворено контрольним read-only вводом, першопричину (конкатенація + `FromSqlRaw`) усунено параметризацією та allowlist для `sortBy`; повторний сценарій і позитивна регресія пройдені, 8 з 8 тестів проходять.
